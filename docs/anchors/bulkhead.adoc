====
Full Name:: Bulkhead, a stability pattern from Michael T. Nygard's _Release It!_

Also known as:: resource isolation, compartmentalisation, pool isolation; at infrastructure scale, cell-based architecture

[discrete]
== *Core Concepts*:

Partition the Resource, Not the Call:: A bulkhead gives each dependency, tenant or workload its own slice of a finite resource -- threads, connections, memory, processes, instances -- so that one slow or failing consumer can only exhaust its own slice. Microsoft's Azure Architecture Center states the goal in one line: "Isolate the elements of an application into pools so that if one element fails, the others continue to function."

The Name Is the Design:: From a ship's hull. Azure: "This pattern is named after the sectioned partitions (bulkheads) of a ship's hull. If the hull of a ship is compromised, only the damaged section fills with water, which prevents the ship from sinking." The ship still takes damage. It does not sink.

The Line Against Circuit Breaker:: A circuit breaker *stops calling* a dependency that keeps failing. A bulkhead *caps how much of the system* any one dependency can consume, whether it fails or merely gets slow. They answer different failure modes and are normally combined -- Azure lists the combination explicitly: "consider combining bulkheads with retry, circuit breaker, and throttling patterns."

Two Implementation Forms:: A *thread-pool bulkhead* gives each dependency its own executor, so a hanging downstream call blocks only that pool -- the classic Hystrix form. A *semaphore bulkhead* caps concurrent calls on the caller's own thread, with no extra pool. Resilience4j documents the trade: its `SemaphoreBulkhead` "should work well across a variety of threading and I/O models. It is based on a semaphore, and unlike Hystrix, does not provide 'shadow' thread pool option" -- and therefore "it is up to the client to ensure correct thread pool sizing that will be consistent with bulkhead configuration."

The Same Idea at Infrastructure Scale:: Separate pods, clusters, accounts or regions per tenant or criticality tier. Azure treats this as the same pattern under a second name: the approach is "also known as a _cell-based architecture_."

Timeouts Are a Precondition:: A bulkhead bounds how many calls can be stuck at once. Without a timeout, "stuck" means forever, and the partition fills up and stays full. The bulkhead then contains the damage instead of preventing it.

[discrete]
== *When to Use*:

* Designing a service that fans out to dependencies with different latency profiles -- a slow third-party payment API next to a fast internal catalogue
* Separating critical from best-effort consumers of the same service, so a batch job cannot starve interactive traffic
* Multi-tenant systems, where the question is which blast radius a single noisy tenant gets
* Reviewing an incident in which one dependency took the whole process down: the missing control is usually a bulkhead, not a retry
* Together with `circuit-breaker` and timeouts, as the stability-pattern set rather than one pattern alone

[discrete]
== *Common Misunderstandings*:

* ❌ "A bulkhead and a circuit breaker do the same job" -- one limits concurrency, the other limits repeated failures; a system with only a breaker still dies of a slow dependency that never fails outright
* ❌ "A bulkhead prevents the failure" -- it bounds the blast radius; the partitioned workload still degrades
* ❌ "Finer partitioning is always safer" -- Azure asks you to "determine the level of granularity for the bulkheads" and to weigh "the overhead in terms of cost, performance, and manageability"
* ❌ "Netflix invented it" -- Netflix popularised it through Hystrix and then moved away from that form; the pattern is Nygard's
* ✓ "A bulkhead is a cap on how much of my system one dependency may consume" -- accurate, and it explains why the hard part is choosing the number
====

== *Criticism*:

* *Static partitioning buys isolation with wasted capacity, and Microsoft prints the condition under which that trade fails.* The Azure Architecture Center lists when not to use the pattern: "Less efficient use of resources might not be acceptable in the project" and "The added complexity isn't necessary." Reserved capacity that sits idle in one partition while another queues is the cost of the guarantee. https://learn.microsoft.com/en-us/azure/architecture/patterns/bulkhead[Microsoft, "Bulkhead Pattern", Azure Architecture Center] (page updated 19 September 2026).
* *The static number is the real objection, and it comes from the organisation that popularised the pattern.* Netflix's own `concurrency-limits` project exists because fixed limits have to be guessed and then go stale: "in large distributed systems that auto-scale this value quickly goes out of date and the service falls over by becoming non-responsive." https://github.com/Netflix/concurrency-limits[Netflix, _concurrency-limits_ README]. Netflix's stated reason for retiring Hystrix is the same shift, toward "more adaptive implementations".
* *The thread-pool form lost its default status on cost grounds.* Resilience4j, the successor Netflix names, makes the semaphore the plain case and drops Hystrix's "shadow" thread pool, pushing pool sizing back to the caller. The extra threads, context switches and memory of a pool per dependency were a price the follow-on library chose not to pay by default. https://resilience4j.readme.io/docs/bulkhead[Resilience4j, Bulkhead documentation].

[discrete]
== *Current Status*:

* *A named pattern in the book, verified in the second edition.* The Pragmatic Bookshelf table of contents for _Release It!_ Second Edition (2018) lists the Stability Patterns as "Timeouts, Circuit Breaker, Bulkheads, Steady State, Fail Fast". https://pragprog.com/titles/mnee2/release-it-second-edition/[_Release It!_ Second Edition, Pragmatic Bookshelf]. The publisher page covers the second edition only; the first edition (2007) is where the stability patterns first appeared.
* *Hystrix is done; Resilience4j is the named successor.* The Netflix README states: "Hystrix is no longer in active development, and is currently in maintenance mode", with no further issue review, merges or releases, and points new projects at Resilience4j while existing ones stay on 1.5.18. https://github.com/Netflix/Hystrix[Netflix/Hystrix]. Polly covers .NET.
* *Naming the term changes the answer.* On a neutral logistics-platform resilience task, one of three no-anchor baselines on `claude-haiku-4-5` proposed bulkheads unprompted and two did not. The term is worth naming.
* *The attribution does not survive the weak tier.* Asked who created the pattern, the same model answered `creator=Netflix (collective); year=2011` -- Hystrix's popularisation, not Nygard 2007. This entry carries the attribution the model does not.
